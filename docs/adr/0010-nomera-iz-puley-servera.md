# 0010. Номера сделок, лидов, клиентов, поставок и отправок выдаёт сервер пулами

## Контекст

В прототипе все номера считаются в браузере по локальному списку (`Д-`, `Л-`, `К-`, `П-`, `ОТ-`). Двое, создающие сделку одновременно, получат один номер (R03.1). При этом связь с сервером может рваться, а работа не должна терять сделанное (R20i.1).

## Решение

Видимые людям номера (`Д-`, `Л-`, `К-`, `П-`, `ОТ-`) выдаёт сервер. Каждый сеанс держит запас из пяти номеров на каждый префикс и пополняет его в фоне; запас выдаётся и при каждой загрузке страницы. Внутренние id (задачи, лента, уведомления, резервы, файлы) строятся из метки сеанса, метки вкладки и счётчика и сервера не требуют. В демо поставщика номеров нет, всё как было.

## Почему

- **Номер с сервера при каждом создании записи** — отвергнут: без связи нельзя создать сделку, а обрыв по требованию не должен терять работу.
- **Метка сеанса и в видимых номерах** — отвергнута: приёмка требует, чтобы номера шли по порядку; метка ломает последовательность `Д-33`, `Д-34`. Для внутренних id порядок не нужен, поэтому там метка годится.
- **Локальный счётчик, как в прототипе** — отвергнут: даёт одинаковые номера у двух людей (то, ради чего всё и делается).

## Последствия

- В номерах бывают пропуски: каждая загрузка страницы забирает пять номеров, и нераспределённые остаются неиспользованными. Приёмка это допускает («пропуски допустимы»); директор может удивиться дырам.
- Номера идут по порядку выдачи, а не по времени создания записи: две сделки, созданные в одну минуту, могут получить номера «наоборот».
- Поведение при пустом запасе без связи в спецификации не описано. Нет данных: что увидит человек, который за обрыв связи создал больше пяти сделок.
- Любая новая сущность с видимым номером обязана идти через общий поставщик, а не считать номер сама.
