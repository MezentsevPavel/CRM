# Архитектура

Выжимка из договора границ сборки, имена сверены с кодом. Почему так решили — `docs/adr/`, слова предметной области — `CONTEXT.md`.

## Поток данных (демо-страница)

- `tools/build.js` склеивает `src/page.html`, `src/css/*.css`, `src/js/*.js` (по имени файла, по возрастанию, в одну функцию с `'use strict'`) и `assets/windsolar-logo.png` (data-URI на место `{{LOGO}}`, место ровно одно) в один `crm-wind-solar.html`.
- Состояние — одна переменная `S` (`let S` в `src/js/50-shell.js`, схема `v:3`). Запуск (`90-boot.js`): `S = startState()` — сохранённое из `localStorage['ws-crm-v3']` (`Store.KEY`) или демо `seed()`; затем `render()`.
- Клик или ввод → обработчик из реестра (`A`, `FORMS`, `ON`) → функция ядра меняет `S` → `render()` перерисовывает раздел целиком, меню, карточку и вызывает `save()`; ввод с клавиатуры — через `saveSoon()` (400 мс).
- Хранение: `Store.dump(S)` пишет JSON без `S.ui` (даты — `{$date}`), без товаров снимка каталога (`Catalog.pack`; они восстанавливаются из констант `CATALOG` и `STOCK_SNAPSHOT`). Не влезло — выкидываются фото приёмки, файлы заявок и фото товаров по одному, сначала новые и крупные.
- `Store.load(raw)` отдаёт `null` при чужой `v` или `rev` ≠ `Store.REV` — тогда берётся `seed()`. `S.ui` (открытая карточка, вкладки, фильтры) не сохраняется.
- `seed()` = база + шаги `SEEDS` по порядку номеров файлов; каждый раздел сеет своё демо.

## Границы модулей

- Ядро (`30`–`48`): `const Имя = (() => { …; return { … }; })()`. Функции принимают состояние первым аргументом `st`, не трогают DOM, `S`, `localStorage`; время приходит аргументом `now`. Проверяется на маленьком состоянии из теста.
- Исключение: `41-feed.js` — ядро `Feed` плюс вид ленты (`feedHtml`, `actNextHtml`, свои `A` и `FORMS`).
- Модель (`20-model.js`): справочники, `seed()`, помощники над `S` (`can`, `me`, `product`, `stockOf`).
- Виды (`50`–`71`): функции `S → HTML-строка` (`v*`, `d*`, `m*`, `*Html`), состояние не меняют, текст из данных идёт через `esc()`. Состояние меняют только `A`, `FORMS`, `ON` и ядро.
- Порядок склейки = номер файла: код верхнего уровня при загрузке видит лишь то, что объявлено раньше; вызовы внутри функций порядка не требуют.

## Реестры — как раздел подключается

Раздел регистрируется в своём файле, чужих не правит (ADR 0002). Пустые реестры объявлены в `50-shell.js`, кроме двух.

| Реестр | Что кладётся |
|---|---|
| `NAV` | `NAV.push({id, label, icon, group, order, hint, ok, badge?})`; группы `GROUPS`, в группе не больше `MAX_GROUP` пунктов |
| `VIEWS` | `VIEWS.<id> = () => html`, `id` как у `NAV` |
| `DRAWERS` | `DRAWERS.<тип> = id => ({kind, title, sub, body})` или `null`; открывает `openDrawer(тип, id)` |
| `MODALS` | `MODALS.<тип> = id => html`; открывает `openModal(тип, id)` |
| `A` | `A['<act>'] = (el, e) => …` — клик по `data-act` |
| `FORMS` | `FORMS['<form>'] = form => …` — отправка `<form data-form>` |
| `ON` | `ON.input['<key>']`, `ON.change['<key>'] = (el, e) => …` — поля с `data-on`, затем `saveSoon()` |
| `SETTINGS_TABS` | `SETTINGS_TABS.push({id, label, order, ok, render})` — объявлен в `59-settings.js` |
| `SIMS` | `SIMS.push({id, label, run})`, `run` → `{text, view, id?}` — кнопки «Пульта проверки» (`64-sims.js`) |
| `SEARCH` | `SEARCH.push({kind, label, find: q => [{title, sub, open}], order?})`; право и видимость проверяет сам `find` |
| `SEEDS` | `SEEDS.push(st => { … })` — демо раздела; объявлен в `20-model.js` |

## Соглашения

- **Одна величина — одна функция ядра**, экран и карточка зовут её, копию формулы не заводят (ADR 0004):
  - остаток и «свободно» — `Stock.summary`; «ждёт приёмки» — `Ships.awaitingReceipt`;
  - сумма сделки — `Deals.total`, сумма списка — `Deals.sumOf`;
  - право — `Perms.can`; кому уведомление — `Notify.RECIPIENTS`, создание — `Notify.push`.
- **Видимость сделок — только `Leads.dealsVisible(st, personId)`** (ADR 0005): список, поиск, клиент, лента, плитки главного экрана (сводка фирмы по праву `firm` считает все сделки). Лиды — `Leads.visible`.
- **Склад меняет только `Stock.move`** (приход, отгрузка, бой, перемещение): остаток и журнал `moves` пишутся вместе. Резерв — `Stock.reserve`, `unreserve`, `release`; списание при продаже — `Stock.sell`, она идёт через `move`.
- **Воронки — данные через `Pipes`** (ADR 0003): `S.pipelines`, виды `Pipes.KINDS` (tasks, deals, leads, ships, dispatch). Запись хранит id этапа, не номер; «закрыто» — флаг `final`, «прибыло» — `arrived`. Этап меняют функции владельца вида: `Leads.move`, `Deals.move`, `Ships.setStage`, `Dispatch.setStage`.
- **Роли и права — данные** (`S.roles`, `S.people[].role`); неизвестное право не открывает ничего.
- **Отправки (`Dispatch`) — не поставки (`Ships`)** (ADR 0006): свои данные `S.dispatches`, своя воронка.
- Нет данных — `null` или `'_'` в данных и «нет данных: <что>» на экране, не 0.
- Поменялась форма записей — поднять `Store.REV` и дописать шаг в `server/migrate.js` (последствия — в `AGENTS.md`).

## Серверная версия

Тот же код страницы и ядра; режим включает `const SERVER` (`00-util.js`): сервер вставляет `window.CRM_SERVER=1` на место метки `<!--CRM-SERVER-->` из `src/page.html`. Без метки страница — демо, как описано выше. Что в рабочей версии скрыто (почта, Telegram, MAX, имитации, «Кто я»), — всё под `if (SERVER)` в видах.

### Поток данных

- **Хранение.** Одна база SQLite (`$CRM_DATA/crm.db`, `server/db.js`). Общее состояние фирмы разложено на документы `(key, id)` — запись массива или значение по ключу (`Docs.split`); таблицы `docs`, `users`, `sessions`, `files`, `file_refs`, `log`, `meta` (список — шапка `server/db.js`). В памяти сервера (`server/sync.js`) то же состояние целиком, грузится из `docs` при старте; пачки идут по одной, гонок нет.
- **Личное не уходит на сервер**: `me`, `view`, `ui`, `rcv`, тема и вид поставок (`Docs.KEYS.LOCAL`); оно лежит в `localStorage['ws-crm-srv:<personId>']`.
- **Вход.** `POST /api/login` → cookie `crm_sid` (в базе только sha256 токена); пароль — scrypt N=2^17 с солью (128 МБ на проверку), параметры записаны в строке хеша (прежние хеши 2^14 проверяются и при удачном входе перехешируются); считаются не больше двух проверок сразу, остальные ждут очереди (`server/auth.js`, `SCRYPT_MAX`); попытки считаются по компьютеру (адрес — последний элемент `X-Forwarded-For` от Caddy, и только если соединение с 127.0.0.1/::1): 5 неудач с адреса по одному логину за 15 минут закрывают этой паре вход, 20 неудач с адреса по любым логинам — адрес целиком; с другого адреса тот же логин входит. Пока `mustChange`, всё, кроме `me`/`password`/`logout`, — 403. Не вошедшему `GET /` отдаёт страницу без закрытых кусков (`CRM_LITE`: только вход); после входа браузер перезагружается за полной.
- **Чтение.** Вкладка получает `GET /api/state` — не общее состояние, а копию, урезанную под человека (`Visible.of`: чужие сделки и лиды, цены без права `prices`, чужие уведомления). Дальше `GET /api/sync?view=<id вкладки>`: сервер помнит, что отдал вкладке, и шлёт только новое, изменённое и исчезнувшее.
- **Запись.** Действие — всё, что изменилось в `S` от прошлого `save()` до этого: `save()` режет его в пачку `Docs.diff(документы прошлого среза, текущие)` с `base` у каждой правки и ставит в очередь вкладки; пачки уходят `POST /api/changes` строго по одной, обрыв связи — плашка «Нет связи» и повтор той же пачки (повтор не задваивает: такой же документ сервер пропускает). Отказ (409, 403) снимает только свою пачку: вкладка собирает `S` из подтверждённого сервером, оставшихся пачек и несохранённого. Сервер на каждую запись: видна ли она человеку → трёхстороннее слияние `Docs.merge` в его урезанной копии → итог накладывается на настоящую запись (скрытое остаётся настоящим) → `Guard.check` (права) → ссылки на файлы → запись всей пачки в одной транзакции и строка в `log`. Нет права — 403 «Нет прав: …»; правки разошлись — 409 с именем того, кто правил, и свежей версией. Всё или ничего.
- **Рассылка.** После пачки сервер шлёт всем открытым вкладкам SSE `seq` (`GET /api/events`); вкладка идёт за разницей в `/api/sync`. Кроме `seq`: `reload` (после восстановления копии) и `bye` (сеанс закрыт).
- **Номера** (`Д-`, `Л-`, `К-`, `П-`, `ОТ-`) выдаёт только сервер (`POST /api/ids`, запас приходит с `/api/state`); браузер берёт их через `Ids.next`, демо — своим счётчиком. Внутренние id вкладка собирает из метки сеанса, поэтому не пересекаются.
- **Файлы.** `POST /api/files` кладёт тело в `$CRM_DATA/files/<id>`; в записи остаётся `{id, name, type, size, url, by, at}` (фото приёмки — строка `url`), `data: null`. Скачать может загрузивший и тот, кто видит запись со ссылкой на файл. Фото товара — `product.photos`, те же файлы: загрузка с `X-File-Kind: photo` и привязка к товару проверяют содержимое (JPEG, PNG, WebP, GIF по первым байтам), список фото правит право «Добавлять товары», файл и поле `photos` отдаются только с правом «остатки». Ссылки считает `file_refs`: брошенный файл удаляется через 7 дней, снятый со всех записей — через 30.
- **Задачи сервера** (`server/jobs.js`, раз в минуту): напоминания о делах и «лид ждёт» (`Acts.notify`, `Leads.notifyWaiting`) — только на сервере, браузер их не запускает; чистка сеансов, забытых вкладок, попыток входа, файлов.
- **Обновление по кнопке.** `server/updater.js` (ADR 0013): директор в «Настройки → Обновление» проверяет и ставит последнюю версию ветки master открытого репозитория `CRM_UPDATE_REPO` — копия базы, архив коммита с GitHub, проверка, замена кода (без `data`), версия в `.crm-version`, выход с кодом 75, поднимают systemd или `start.cmd`. Вкладки узнают о новой странице из события `build` потока `/api/events`. В рабочей копии с `.git` кнопка не заменяет код.
- **Копии.** `server/backup.js`: ночью (`CRM_BACKUP_HOUR`) `VACUUM INTO` в `$CRM_DATA/backups`, хранится `CRM_BACKUP_KEEP`; пропущенная копия делается при старте. Файлы фирмы в копию не входят. Восстановление переписывает таблицы работающей базы из копии (всё или ничего), перед ним снимается копия текущей, вкладкам идёт `reload`. Делает директор: «Настройки → Копии» или `server/admin.js`.
- **Перенос.** Директор грузит CSV остатков и клиентов в «Настройки → Перенос»; браузер разбирает таблицу (`Import.decode`, `parseCsv`, `stockRows`, `clientRows`) и шлёт строки на `POST /api/import/stock|clients`; сервер применяет их (`Import.applyStock`, `applyClients`). Остатки заменяют прошлый перенос (клетка, где остаток был больше нуля, а стал 0 или пропал из файла, пишет «Ввод остатков» с остатком 0), клиенты сливаются по ИНН, телефону, почте, ID Битрикса; строка без всего этого, но с именем заведённого клиента (`Import.twins`: без регистра, пробелов и «ё/е», при компании у обоих — и она) показывается как «Возможно, уже есть» с выбором «тот же» (по умолчанию, данные дополняют клиента) или «новый» (`fresh: true` в строке). В тот же список попадают строки, где имя совпало, но у обоих разные ID Битрикса (по умолчанию «новый»; «тот же» — `same: true`: ID клиента остаётся, ID из файла идёт в `bitrixAlso` и в ленту), и повторы без контактов внутри файла («в файле дважды», по умолчанию один клиент).

### Границы и договорённости

- **Ядро считает один раз для экрана и сервера**: `server/runtime.js` грузит `src/js` в `node:vm` (`tools/vm-load.js`), сервер зовёт `Docs`, `Visible`, `Guard`, `Import`, `Perms`, `Leads`, `Acts`, `Stock`, `Catalog` оттуда; отдельной серверной копии правил нет.
- **Права и видимость — на сервере.** Браузер прячет кнопки, но решает `Guard.RULES[ключ]` (по `Perms.can` и видимости записи). Ключ состояния, которого нет в `Docs.KEYS` или `Guard.RULES`, пишет только директор. Остатки (`stock`, `aside`) напрямую не меняются: изменение должно сойтись с суммой новых `moves` той же пачки.
- **Клиентов не удаляют, а объединяют.** `Clients.merge` переводит на первого всё, что ссылается на второго (сделки и лиды `clientId`, ленту, дела, уведомления), дополняет его контакты и пишет в его ленту запись вида `merge` с `data.dropId`. Guard пускает удаление клиента только вместе с такой записью, если человек правит клиентов, видит и может править всё переезжающее (`Clients.mergeBlock`) и в итоге пачки на удалённого ничего не ссылается; иначе 403 целиком. Уведомления, которых человек не видит, переводит сервер сам (`cascadeMerge` в `server/sync.js`).
- **Слияние идёт с базой из `Visible.of` этого человека**, иначе вырезанные `'hidden'` и «цена скрыта» записались бы поверх настоящих значений. Каскад нового имени клиента в невидимые человеку сделки делает сервер.
- **Закрытые куски.** Каталог с ценами, остатки и демо-записи не должны уходить не вошедшему: сборка метит их `/*CRM-GATE-…*/`, сервер вырезает (`stripGated`) и ставит заглушку с теми же именами. Страница в обоих видах — один файл `crm-wind-solar.html`.
- **Ревизия формы записей.** В браузере демо смена `Store.REV` стирает сохранённое; на сервере база ревизии меньше `REV` доводится шагами `MIGRATIONS` из `server/migrate.js`, нет шага — сервер не стартует и говорит почему; база новее кода — тоже отказ. Данные при отказе не меняются.
- **Секреты.** Хеши, соли, токены не попадают в состояние, ответы и журналы.
- **Запрет посторонних скриптов.** Страница и ответы несут `Content-Security-Policy` (`server/app.js`, `pageCsp`): скрипты — только встроенные страницы по sha256-хэшу, посчитанному с отдаваемого текста (ни `unsafe-inline`, ни `unsafe-eval`); подключения — к себе; картинки — свои, `data:`, `blob:`; шрифты — свои и `data:`; `frame-ancestors`, `object-src`, `base-uri` — `'none'`. Поэтому в коде страницы нельзя `onclick=` и прочие обработчики в атрибутах, `eval`, `new Function`, `javascript:` (тест это проверяет); обработчики вешаются через `data-act`, `data-on`, `data-form`. Стили встроены и в `style=`, поэтому для стилей `unsafe-inline` остаётся.
- **Установка.** `deploy/install.sh` (Ubuntu 24.04, root): Node, Caddy (домен → `127.0.0.1:3000`), пользователь `crm`, код в `/opt/crm`, данные в `/var/lib/crm`, служба `crm`; `deploy/update.sh` меняет код и сборку, данные не трогает, при неудачном запуске возвращает прежнюю версию. Инструкция для не программиста — `docs/server-install.md`.
- **Тесты сервера** идут без HTTP-обёрток там, где можно: ядро — `load()`, сервер — `createApp({ dataDir: временная папка, port: 0 })` и `fetch` (`tests/server-kit.js`), браузерный режим — `load({ globals: { CRM_SERVER: 1, fetch, EventSource } })` с поддельными `fetch` и `EventSource`.
