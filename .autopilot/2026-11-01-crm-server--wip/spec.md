# Спецификация: серверная CRM wind-solar с общей базой

## Задача

Прототип CRM живёт в одном браузере: у каждого своя копия данных, «Кто я» выбирает любой, права только прячут кнопки. Фирма в нём работать не может. Нужна та же CRM, но на своём сервере в России: одна база на всех, вход по логину и паролю, права проверяет сервер, файлы лежат на сервере, уведомления доходят до другого компьютера, копии базы делаются каждый день, вход по https. Сервер и домен директор арендует сам. Настоящие остатки и клиенты переносятся в базу. Почта, Битрикс, Telegram и MAX — следующий этап.

## Решение

- Директор открывает `https://<домен>` (нет данных: домен), вводит логин и пароль и видит ту же CRM, что в прототипе, только с данными фирмы: без примеров, без «Кто я», без «Пульта проверки», без почты и «Сообщений клиентам».
- Сотрудников заводит директор в «Сотрудниках»: имя, роль, логин; CRM выдаёт временный пароль, который сотрудник меняет при первом входе.
- Что один сделал, другой видит через пару секунд без перезагрузки; уведомление приходит со звуком и всплывает на экране, если вкладка CRM открыта.
- Сотрудник получает с сервера только то, что ему положено по роли. Запись, которую ему нельзя менять, сервер не принимает, даже если обойти кнопки.
- Файлы и фото приёмки хранятся на сервере.
- Каждую ночь сервер делает копию базы и держит 30 последних. Директор скачивает любую и восстанавливает базу из «Настроек».
- В «Настройках → Перенос» директор загружает CSV листа «Остатки» и CSV клиентов из Битрикса. Сначала видит, что будет загружено, потом подтверждает.
- Для установки есть скрипт и пошаговая инструкция по-русски: арендовать VPS, направить домен, выполнить три команды.
- Демо-прототип одним файлом остаётся для показа и проверок.

## Решения по реализации

- **Стек — Node 24 без npm-зависимостей**: `node:http`, `node:sqlite`, `node:crypto` (`scrypt`), `node:zlib` не нужен. Почему: правило проекта «ничего не ставится»; на сервере ставятся только Node и Caddy, оба называются в инструкции.
- **https — Caddy** перед Node: получает сертификат Let's Encrypt сам, проксирует на `127.0.0.1:3000`. Почему: ноль ручной работы с сертификатами.
- **Сервер держит всё состояние фирмы в памяти** (тот же объект, что `S` прототипа, без личного), грузит его из SQLite при старте и пишет изменённые документы в транзакции. Один процесс, правки применяются по одной — гонок внутри сервера нет. Почему: фирма маленькая (десятки человек, мегабайты данных); проще и надёжнее любой схемы с запросами.
- **Ядро прототипа (`src/js`) грузится на сервере** тем же приёмом, что `tests/load.js` (`node:vm` с заглушками DOM). Сервер зовёт `Perms`, `Leads.dealsVisible`, `Stock`, `Acts.notify`, `Leads.notifyWaiting`, `Import` — экран и сервер считают одним кодом.
- **Синхронизация документами**: состояние режется на документы — запись массива по `id`, запись словаря (`stock`, `aside`) по ключу, остальные ключи верхнего уровня целиком. Браузер после каждого `save()` сравнивает `S` с последней подтверждённой сервером копией и шлёт изменённые документы пачкой `{key, id, base, data|deleted}`. Сервер на пачку: трёхстороннее слияние с текущей версией (поля объекта — по отдельности, массивы записей с `id` — по `id`), проверка прав `Guard`, запись всего или ничего. Почему не «команды в ядро»: 60 из 114 обработчиков правят `S` напрямую, для задач, приёмки, поставок, справочников ядра нет — переписывать дороже, а проверки прав всё равно пишутся заново.
- **Права на запись — `Guard`**, правило на каждый ключ данных `S` (таблица в `interfaces.md`), на основе `Perms.can` и функций видимости ядра. Склад (`stock`, `aside`, `moves`): журнал `moves` только дополняется; изменение остатка должно сойтись с суммой новых движений той же пачки; вид движения — по праву (приход — `receive`, продажа — `sell`, перемещение — `logistics` или `dispatch`, бой — `stock`, ввод остатков — `admin`). Неизвестный ключ — только директор.
- **Права на чтение — `Visible.of(st, personId)`**: урезанная копия состояния для человека — сделки по `Leads.dealsVisible`, лиды по `Leads.visible`, клиенты по видимости клиента (переносится из вида в ядро), задачи по видимости задачи (из `20-model.js` в ядро), лента и дела — по видимости родителя, резервы — без номера сделки, если сделка не видна, уведомления — свои (директор с `firm` — все), цены вырезаны без права `prices`, почты и сообщений клиентам нет. Сервер помнит, что уже отдал сеансу, и шлёт разницу: новое, изменённое, исчезнувшее.
- **Живые обновления — Server-Sent Events** (`/api/events`): сервер шлёт «есть новое», браузер забирает разницу. Почему SSE: встроено в браузер, само переподключается, Caddy пропускает без настройки.
- **Номера** (`Д-`, `Л-`, `К-`, `П-`, `ОТ-`) выдаёт сервер: сеанс держит запас из пяти номеров на каждый префикс и пополняет его в фоне. Внутренние id (задачи, лента, уведомления, резервы, файлы) — уникальные с меткой сеанса, без обращения к серверу. В демо всё как было.
- **Личное вне общей базы**: «кто я» — из сеанса; раздел, тема, настройки таблицы поставок и черновик приёмки — в браузере; включённые виды уведомлений и звук (`prefs.notify`, `prefs.sound`) — общие, каждый правит только свою строку (по ним другие компьютеры решают, кому слать).
- **Системные уведомления по времени** (`Acts.notify`, `Leads.notifyWaiting`) в серверном режиме идут только на сервере, раз в минуту; браузер их не запускает.
- **Файлы** — `POST /api/files` (тело — файл, имя в заголовке), диск `data/files/<id>`; в записи — `{id, name, type, size, url, by, at}` без содержимого. Предел 20 МБ. Фото приёмки загружаются сразу после сжатия. Скачать может загрузивший или тот, кто видит запись со ссылкой на файл.
- **Сеансы** — cookie `HttpOnly`, `SameSite=Lax`, `Secure` за https; пароль — `scrypt` с солью; на запись — заголовок `X-CRM: 1` (защита от чужих форм). Хеши паролей и сеансы — только в таблицах сервера, в состояние не попадают.
- **Копии** — `VACUUM INTO` в `data/backups/crm-ГГГГ-ММ-ДД.db` в 03:00 по `TZ` сервера (по умолчанию `Asia/Irkutsk`, правится в настройке службы), 30 последних. Файлы не копируются: они не перезаписываются, удалённые лежат 30 дней — любая из 30 копий с ними согласована. Платный бэкап хостера — совет в инструкции.
- **Схема сервера**: таблицы `docs(key, id, data, ver, seq)`, `meta` (номер правки `seq`, ревизия, счётчики номеров), `users(personId, login, hash, salt, mustChange, disabled)`, `sessions`, `files`, `file_refs`, `log(seq, at, personId, key, id, op)`, `attempts`. Ревизия формы записей в серверной базе **никогда не стирает данные**: несовпадение — миграция из реестра миграций или отказ запуска с понятным текстом.
- **Режим страницы**: сервер вставляет в отдаваемую страницу метку серверного режима; без метки страница — демо. Одна сборка, один файл.
- **Шрифты** — `woff2` Manrope (400–800) и JetBrains Mono (400, 500), наборы `cyrillic`, `cyrillic-ext`, `latin`, `latin-ext`, скачиваются один раз с `fonts.gstatic.com` по ссылкам из CSS Google Fonts (запрос с заголовком браузера, чтобы получить `woff2`), кладутся в `assets/fonts/` с файлом лицензии OFL; сборка встраивает их в CSS страницы (`data:`-адреса, как логотип); Google Fonts из страницы убран. Почему встроены, а не отдельными файлами: одна сборка и для сервера, и для демо, ноль внешних адресов в обоих.

### Колонки переноса

- **Лист «Остатки»** (CSV из Google-таблицы «Выгрузка с корса общая»): строка заголовков ищется среди первых 10 строк — та, где есть хотя бы две из колонок «Склад ИП», «НПП», «ВС», «ответхранение», «В пути», «Бой», «Резерв» (без учёта регистра и пробелов). Колонка названия — первая из «Наименование», «Номенклатура», «Товар», «Название», «Модель», иначе первая текстовая колонка. Строка с названием и без единого числа — раздел (`cat`, вложенность через « › », как в `STOCK_SNAPSHOT`). Пустая клетка — `null`, текст в числовой клетке — `null` и строка в «неразобранные». Образца файла в репозитории нет: тесты — на искусственном CSV той же формы.
- **Битрикс, контакты**: «ID», «Имя», «Фамилия», «Отчество» (имя клиента — «Фамилия Имя Отчество» из непустых); телефоны — каждая колонка, в названии которой есть «телефон»; почта — первая непустая колонка с «e-mail»/«email»/«почта»; «Адрес»; «Компания» и «Должность» → `org`; «Ответственный» → менеджер клиента, если совпал с именем сотрудника CRM, иначе пусто.
- **Битрикс, компании**: «ID», «Название компании»; телефоны и почта — так же; «ИНН», если колонка есть; «Адрес», «Фактический адрес», «Юридический адрес» — первый непустой; «Ответственный» — так же.
- `bitrixId` — значение «ID», хранится у клиента для будущей связи с Битриксом.
- **Перенос** — разбор CSV (кодировка, разделитель, кавычки) и превращение строк в товары, остатки, резервы, клиентов — функции ядра `Import`; предпросмотр считает браузер директора, загрузку исполняет сервер той же функцией. Товары листа без пары в каталоге получают id по нормализованному названию — повторный перенос попадает в те же товары.

| Требование | Почему не сейчас |
|---|---|
| Почта, Битрикс, Telegram, MAX (R15) | следующий этап — по брифу; в рабочей версии скрыты, демо их показывает |

| Архив всех файлов одной кнопкой | копии — «базы» по брифу; файлы защищены 30-дневным хранением удалённых и бэкапом хостера |
| Уведомления при закрытом браузере (Web Push) | раунд 1, «ок»: нужны серверы Google и Apple — против 152-ФЗ |
| Установка на сервер руками сборки | необратимое и внешнее действие — только по «да» директора после сдачи; сама сборка этого не делает |
| Проверка `install.sh` запуском | на этой машине нет Linux (ни WSL, ни Docker) — только проверка синтаксиса `bash -n`; первый запуск — у директора по инструкции |
