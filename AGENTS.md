# CRM wind-solar

Внутренняя CRM фирмы wind-solar (солнечные станции), для директора и сотрудников по ролям. Два вида из одного кода страницы: кликабельный прототип (один HTML-файл, демо в браузере) и рабочая серверная версия (`server/`: общая база SQLite, вход, права на сервере, файлы, копии, установка на Ubuntu).

Устройство — `docs/architecture.md`; почему так — `docs/adr/`; термины — `CONTEXT.md`; поставить на сервер — `docs/server-install.md`.

## Команды

Нужен только Node 24; `package.json` нет, ничего не ставится.

| Команда | Что делает |
|---|---|
| `node tools/build.js` | собирает `crm-wind-solar.html` из `src/` и `assets/` |
| `node --test tests/` | все тесты (569), около 180 с |
| `node --test tests/stock.test.js` | один файл тестов (любой `tests/*.test.js`), около 4 с |
| `node tools/serve.js 5179` | демо-страница на `http://localhost:5179` (сам не собирает) |
| `CRM_PORT=5181 node server/main.js` | серверная версия на `http://127.0.0.1:5181`; читает собранный файл один раз при старте — после `build.js` перезапустить |
| `node server/admin.js create-director` | завести директора (имя, логин, пароль дважды); без него в пустую базу не войти |
| `node server/admin.js reset-password <логин>` | выдать новый пароль (показывается один раз, при входе его меняют) |
| `node server/admin.js backups` | список копий базы (хранится 30 последних) |
| `node server/admin.js restore <имя копии> --yes` | заменить базу копией; сперва снимается копия текущей; сервер потом перезапустить |

Для сервера и `admin.js` свои проверки гоняй на временной папке: `export CRM_DATA=<папка вне репозитория>` (без неё — `./data`, она в `.gitignore`). Порт 5178 — показ пользователю, 5179 и 5181 — свои проверки.
Перед сдачей: `node tools/build.js && node --test tests/`.
Установка на Ubuntu — `deploy/install.sh <домен>` и `deploy/update.sh` (на этой машине не запускались, проверен только `bash -n`); на сервере `install.sh` ставит команду `crm-admin` = `admin.js` с настройками службы.

## Где что

- `src/js/50-shell.js` — оболочка: состояние `S`, `render()`, меню `NAV`, реестры `A`, `FORMS`, `ON`, `DRAWERS`, `MODALS`, `SEARCH`, `SIMS`, события.
- `src/js/20-model.js` — `seed()` (демо), `seedBase()` (пустая рабочая база: роли, воронки, каталог), `SEEDS`, помощники `can()`, `me()`, `product()`. `src/js/30-store.js` — сохранение в браузере, `REV`.
- `src/js/31`–`44` — ядро без DOM, модуль на файл: Perms 31, Pipes 32, Stock 33, Ships 34, Leads 35, Mail 36, Notify 37, Catalog 38, Dispatch 39, Clients 40, Feed 41, Deals 42, Acts 43, Attach 44.
- `src/js/45`–`48` — ядро сервера, тоже без DOM: `Docs`/`Ids` 45 (разбор состояния на документы, слияние, номера), `Visible` 46 (что видит человек), `Guard` 47 (кто что может записать), `Import` 48 (CSV остатков и клиентов).
- `src/js/51`–`71` и `src/css/` с тем же номером — виды: Сегодня 51, Задачи 52, Товары 53, Поставки 54, Приёмка 55, Сделки 56, Сообщения 57, Сотрудники 58, Настройки 59 и 62–68, Лиды 60, Почта 61, Пульт 64, Отправки 69, Клиенты 70, Файлы у записей 71. `72-server.js` — серверный режим в браузере (вход, синхронизация), `73-transfer.js` — «Настройки → Перенос», `74-backups.js` — «Настройки → Копии».
- `server/` — `main.js` запуск; `app.js` HTTP API и выдача страницы (`createApp`, `openCore`); `sync.js` пачки изменений; `auth.js`; `files.js`; `backup.js`; `jobs.js` (раз в минуту); `db.js`; `migrate.js`; `runtime.js`; `admin.js`.
- `tools/build.js` сборка и закрытые куски; `tools/vm-load.js` — загрузка `src/js` в `node:vm` (тесты и сервер); `assets/fonts/` — шрифты (woff2 + `fonts.css`, встраиваются при сборке).
- `tests/load.js` — шов тестов ядра и страницы: `load()` и `bootPage(html)`; `tests/server-kit.js` — поднимает сервер во временной папке для тестов; `tests/index.js` сам подхватывает каждый новый `tests/*.test.js`.

## Подводные камни

- `crm-wind-solar.html` — результат сборки, лежит в git, руками не правится; `tests/foundation.test.js` сверяет его со сборкой, так что после любой правки `src/` или `assets/` — `node tools/build.js`, иначе красный.
- `Store.REV` (`src/js/30-store.js`, сейчас 16): в демо-браузере другая ревизия молча стирает сохранённое (`Store.load` даёт `null`, берётся `seed()`). Рабочая база лежит на сервере и не стирается: `meta.rev` меньше `REV` — нужен шаг `MIGRATIONS[n]` в `server/migrate.js` (реестр пока пуст), иначе сервер откажется стартовать. Поднимать, когда меняется форма записей, роли, права, воронки; причину дописать строкой над `REV`. Забыл поднять — тесты не заметят (сравнивают `REV >=`).
- Новый ключ верхнего уровня `S`: куда он — решить в `Docs.KEYS` (`45-sync.js`) и в `Guard.RULES` (`47-guard.js`); неизвестный ключ на сервере пишет только директор. Права проверяет сервер, браузер лишь прячет кнопки.
- Закрытые куски: `tools/build.js` оборачивает в метки `/*CRM-GATE-OPEN*/ … /*CRM-GATE-STUB …*/ /*CRM-GATE-CLOSE*/` снимки `10-catalog-data.js`, `11-stock-data.js`, шаги `SEEDS.push(…)` и демо-команду в `seed()`. Не вошедшему сервер отдаёт страницу без них (`CRM_LITE`, только вход) — код вне меток не должен падать на пустых `CATALOG.rows` и `STOCK_SNAPSHOT.rows`. Шаг `SEEDS.push(` начинается и кончается в первой колонке, иначе сборка падает. Метки руками не ставить.
- На сервере `src/js` (кроме `90-boot.js`) грузится в `node:vm` через `tools/vm-load.js` с `CRM_SERVER=1`: код ядра 31–48 не должен трогать DOM, `window`, `localStorage`. Всё серверное в видах — под `if (SERVER)` (`00-util.js`), демо-ветка ведёт себя как прежде.
- Настоящие CSV клиентов (Битрикс) и остатков в git не кладутся и через сборку не идут: директор грузит их в CRM («Настройки → Перенос»). В тестах — искусственные таблицы, собранные в самом тесте; пароли и хеши нигде не пишутся, тестовые пароли генерируются в тесте.
- Кириллицу не править через PowerShell `Get-Content`/`Set-Content` — кодировка ломается; правка файлов — через Edit/Write.
- Порог размера сохранения — `tests/stock.test.js`, тест «сохранение без снимка…»: `text.length < 340000` после `seed()`, рос вместе с демо. Покраснел — сначала проверь, что рост не из-за товаров снимка каталога (рядом проверка, что их в сохранении нет), потом поднимай.
- `src/js/*.js` склеиваются по имени в одну функцию: имена верхнего уровня общие (повтор `const` роняет всю страницу), код верхнего уровня при загрузке видит только то, что объявлено в файлах с меньшим номером. В `90-boot.js` логики нет и быть не должно: тесты и сервер его не грузят.
- `src/js/10-catalog-data.js`, `11-stock-data.js` — снимки таблиц: руками не править, целиком не читать (сотни длинных строк).
- Нет данных — на экране «нет данных: <что>», не 0 и не прочерк; демо помечено «демо» или «пример»; наружу ничего не уходит, внешних адресов в странице нет (шрифты локальные).

## Окружение сервера

Переменные читают `server/main.js` и `server/backup.js`; в службе их ставит `deploy/install.sh`. Значения не хранить в git.

- `CRM_PORT`, `CRM_HOST` — порт и адрес (по умолчанию 3000 и 127.0.0.1; снаружи ходят через Caddy).
- `CRM_DATA` — папка данных: `crm.db`, `files/`, `backups/` (по умолчанию `./data`, в `.gitignore`); её же читает `admin.js`.
- `CRM_SECURE_COOKIE` — `1`: cookie входа только по https (в службе включено).
- `CRM_FILE_MAX_MB` — предел размера загружаемого файла (по умолчанию 20).
- `CRM_BACKUP_HOUR`, `CRM_BACKUP_KEEP` — час ночной копии и сколько копий хранить (по умолчанию 3 и 30).
- `TZ` — часовой пояс сервера: по нему идут ночные копии и тексты сроков в уведомлениях.

## Как здесь работает Autopilot

Сборка ведётся навыком `/autopilot`. Требования, спецификация и таски — в `.autopilot/`.
Прогресс — `.autopilot/dashboard.html`. Требование из `manifest.md` может снять
только пользователь. Прерванную сборку продолжает «продолжи автопилот».

### Правка без автопилота

Мелкий баг или доводка после сборки — обычная сессия, без прогона.

Сначала прочитай:
1. `.autopilot/PROGRESS.md` — что не доделано, известные баги, о чём договорились с пользователем.
2. Что правили после последней сборки — первая строка таблицы в «История git».
3. Только если правка их касается: почему сделано так — `docs/adr/`; что значат слова — `CONTEXT.md`;
   что именно просили — `manifest.md` в папке сборки (указана в начале `PROGRESS.md`).

После правки:
- коммит — по правилам из «История git»;
- строка в «Правки без автопилота» в `PROGRESS.md`: дата — что — почему;
- починенный пункт из «Не доделано» или «Известные баги» — удали;
- договорились с пользователем о том, что следующая сборка не должна пересматривать, —
  строка в «Договорились», его словами.

### История git

Целиком не читай — бери срез под вопрос:

| Вопрос | Команда |
|---|---|
| что правили после последней сборки | `git log --oneline "$(git log -1 --format=%h --grep='^Autopilot: сборка сдана')"..HEAD -- . ':(exclude).autopilot'` |
| всё, что делали ради требования | `git log --oneline --grep="R02"` |
| история файла | `git log --oneline -10 -- <файл>` |
| когда появился или исчез код | `git log --oneline -S "<фрагмент>"` |
| почему строка такая | `git blame -L <с>,<по> <файл>`, затем `git show <sha>` |
| что внутри коммита | `git show --stat <sha>` |

Срез длиннее ~30 коммитов — отдай его субагенту и возьми выжимку в десять строк.

Коммит: заголовок — что (`fix: даты в одном формате`), тело — почему, трейлер
`--trailer "Requirements: R02"`, если правка касается требования из `manifest.md`.
Заголовок `Autopilot: сборка сдана` пишет только автопилот — по нему находят последнюю сборку.
